## Learned User Preferences

- Обновлять долговременную память проекта через поток continual-learning (memory-updater), а не править `AGENTS.md` параллельно в том же сценарии без необходимости.
- Ожидать рабочую сборку, осмысленное снятие TODO и исправление предупреждений без массовых `eslint-disable` / заглушек.
- Для приёмки важны ручной прогон на localhost и совместимость с локальным Docker/env из `.env.example`.
- `.env` в воркспейсе всегда есть (в `.gitignore`). Меняя для локальной разработки переменные окружения, секреты или ключи фичефлагов, править **оба** файла: `.env.example` и `.env`, не только шаблон.
- Общение с ассистентом в чате — на русском; код, UI-копирайт и доки — по языку проекта и принятым в репозитории конвенциям.
- Схемы в markdown-файлах репозитория предпочтительно оформлять в **Mermaid**, а не ASCII-блоками; исключение — **tree-view** (например обзор дерева проекта), где ASCII уместен.
- При вопросах «сделано ли по PRD/ROADMAP» опираться на **фактическую реализацию в коде**, а не на формальные отметки выполненности в markdown-документах.
- Не принимать «MVP-послабления»: ожидание — полный объём PRD/ROADMAP/spec без урезаний; не использовать в документах и обоснованиях риторику «MVP / после релиза» вместо фактической полноты поведения.
- Регистрационный сбор при фиксированной продуктовой сумме — константа в рублях в бизнес-правилах/коде, без отдельного сервиса динамической конвертации по курсу ЦБ, пока явно не требуется иное в PRD.
- Не сводить «чистоту» проекта только к ESLint: учитывать **`npm run typecheck`** и замечания TypeScript в панели Problems в IDE — они могут не совпадать с выводом `npm run lint` по корню.
- Запуск ESLint — через **`npm run lint`** или **`./node_modules/.bin/eslint`** из корня после `npm ci`; голый **`npx eslint`** вне корректно установленного проекта может подтянуть другую версию ESLint и давать иной результат.
- При синхронизации `docs/` и `spec/` в рамках задачи не дополнять документы «обнаруженными в коде» расхождениями, если эти места не менялись в текущей сессии работы — отражать только объём фактически выполненных в ней изменений.

## Learned Workspace Facts

- Воркеры BullMQ (`startSLAWorker`, `startPaymentWorker`) стартуют из `src/instrumentation.ts` в `register()` при `NEXT_RUNTIME === "nodejs"`, `CI !== "true"` и **`ENABLE_BULLMQ_WORKERS === "true"`** (значение обязательно в окружении и валидируется в `src/env.ts`). В `docker-compose.yml` для сервиса `app` задано `ENABLE_BULLMQ_WORKERS=true`; в `.env.example` по умолчанию `false` — воркеры не поднимаются, пока не выставить `true`.
- В `slaWorker` и `paymentWorker` используются ленивое создание очередей и в `src/lib/redis.ts` у IORedis включён `lazyConnect`, чтобы при `next build` не было подключения к Redis и ошибок `ECONNREFUSED`.
- SLA в очереди завязаны на сценарии: первый отклик, дедлайн оплаты после подтверждения намерения, передача резюме, SLA подтверждения отмены соискателем, дедлайн решения компании.
- Платёжная очередь обрабатывает capture после принятия оффера, возвраты, payout и автопродление PRO ЮKassa (`subscription-renewal` на конец оплаченного периода, `subscription-renew-retry` при неудаче; планирование в `subscriptionRenewalScheduler.ts`, обработка в `paymentWorker`); для выплат используется `User.yookassaPayoutDestination`, для локального мока — `YOOKASSA_PAYOUT_MOCK_WALLET`.
- События ЮKassa обрабатываются через модуль `yookassaWebhookHandlers`; мок-поток оплаты: страница `/pay/mock` и `POST /api/pay/mock-complete`; при `FEATURE_REAL_PAYMENTS=true` HTTP-вебхук проверяет Basic Auth из `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`.
- Эскроу по заявкам с вознаграждением в коде и в `docs/`/`spec/` ведётся через **ЮKassa Safe deal** (HTTP-слой сделок); термин **Escrow** — внутреннее имя защищённой оплаты (деньги удерживает провайдер). Регистрация, подписка PRO и разовый токен отклика остаются обычными платежами Payments API — см. `spec/spec-data-payments-escrow.md`.
- Исходящих email-уведомлений из сервиса нет. Опциональная связь с модерацией для пользователя — публичная ссылка в клиенте (`NEXT_PUBLIC_MODERATION_CONTACT_URL`).
- Клиент Prisma создаётся в `src/lib/prisma.ts` с драйвером PostgreSQL через `@prisma/adapter-pg` и пул `pg` (требование Prisma 7 для engine type client). Если IDE показывает «нет экспорта `Prisma`» из `@prisma/client`, сверять наличие сгенерированного `node_modules/.prisma/client` после `prisma generate` и при необходимости тип колбэка `$transaction` задавать через вывод из `typeof prisma` или общий helper в `src/lib/`.
- Обязательное правило `.cursor/rules/organic-redesign.mdc`: правки без обратной совместимости и без комментариев о прошлой реализации; после изменений `schema.prisma` в агентском режиме локальную БД приводят к согласованному состоянию через сброс/полное применение схемы, без «полу-применённого» состояния для ручного теста; не плодить инкрементальные миграции Prisma ради совместимости — сводить изменения к актуальной `schema.prisma` и согласованной базовой миграции при работе по этому правилу.
- При изменениях, затрагивающих статус фич или публичный контракт, обновлять `docs/ROADMAP.md` в той же логической единице работы вместе с `docs/` и `spec/` (см. `.cursor/rules/documentation-sync.mdc`).
- Если `node_modules/.bin/next` или `tsc` оказались обычными файлами вместо симлинков и падают с неверными относительными путями, обычно помогает чистая переустановка: `rm -rf node_modules && npm ci`.
